Fundamento metodológico Detalle técnico

El motor determinístico (ai_layer/risk_scoring.py) calcula el perfil declarado y el Risk Gap sin LLM: misma entrada → misma salida, auditable. Corre en paralelo a la IA y se cruzan (combine_risk_gaps). Teoría completa en docs/RISK_SCORING_THEORY.md.

Rúbrica del perfil declarado (willingness vs ability)

La voluntad de tomar riesgo (lo que el cliente quiere) y la capacidad (lo que su situación soporta) se calculan por separado en [0,1]. El riesgo efectivo es el mínimo: la capacidad acota la tolerancia. 

willingness = 0.6 · tolerancia      + 0.4 · objetivo
ability     = 0.4 · capacidad       + 0.3 · horizonte
            + 0.2 · liquidez_inv    + 0.1 · experiencia

riesgo_efectivo = min(willingness, ability)      # capacidad acota tolerancia
perfil          = banda_de_20(riesgo_efectivo·100)  # 5 perfiles
gap_interno     = |banda(willingness) − banda(ability)|   # tensión declarada
gap_revelado    = caída de perfil bajo estrés (open_risk_reaction)
gap_level       = bandas(max(gap_revelado, gap_interno))  # 1→low, 2→medium, ≥3→high

Todas las entradas vienen del KYC (scores 1–10, horizonte en años, liquidez 3/5/8, experiencia y objetivo categóricos). La señal revelada se infiere léxicamente de la respuesta abierta al escenario de estrés.

Pasos 2–4 · Perfil del cliente & aprobación de riesgo
De las respuestas del cliente al perfil aprobado por el asesor
La IA propone un perfil preliminar; el asesor lo aprueba, lo modifica o lo rechaza. El perfil aprobado conduce todo lo de abajo.
2. Envío del KYC — POST /cases/{case_id}/kyc

Valores por defecto razonables para el demo. Todos los campos son editables. El backend valida rangos (edad 18–120, scores 1–10, horizonte > 0, etc.).

3. Análisis de perfil con IA — POST /cases/{case_id}/ai/profile-analysis

Si kyc_submission_id queda vacío, el backend usa case.current_kyc_submission_id. Requiere OPENAI_API_KEY en el entorno del backend; sin ella, devuelve 400 — usar el smoke check como alternativa.

4. Aprobación del perfil por el asesor — POST /cases/{case_id}/profile-approval

proposed_profile se prellena con el último análisis si existe. approved_profile: vacío en approve (el backend lo completa) y en reject; requerido en modify.

Pasos 5–6 · Universo de inversión
Capturar preferencias, filtrar instrumentos elegibles
Traduce las preferencias del cliente al universo de instrumentos sobre el que va a trabajar el optimizador.
5. Preferencias de inversión — POST /cases/{case_id}/investment-preferences

Modo manual con JSON en structured_preferences. Para extracción NLP (IA), borrá el JSON y poné texto en el textarea; si están ambos, gana el structured y el texto queda como contexto.

6. Filtro del universo — POST /cases/{case_id}/universe-filter

Aplica las preferencias vigentes al CSV del universo vía PreferenceFilterEngine. Si preference_id queda vacío → usa la preferencia actual del caso.

Pasos 7–9 · Decisiones del asesor
Propuesta, firma del override, selección final
Si una variante candidata excede el presupuesto de riesgo aprobado, el asesor debe firmar un override por escrito antes de poder seleccionarla.
7. Propuesta de cartera — POST /cases/{case_id}/portfolio-proposal

Genera las variantes DEFENSIVE / BALANCED / GROWTH a partir del filtro actual + el perfil aprobado actual.

8. Firma del override — POST /cases/{case_id}/override-approval

Aprobar / rechazar el override de una variante que excede el presupuesto de riesgo aprobado (típicamente GROWTH). Si la propuesta actual tiene una variante que requiere override, queda pre-seleccionada.

9. Selección de cartera — POST /cases/{case_id}/portfolio-selection

La selección final del asesor. Si la variante requiere override, pasá un override_approval_id aprobado (current si lo dejás vacío). Si la variante no requiere override, dejá el campo vacío.

Pasos 10–11 · Entregable al cliente
Un reporte revisable — no es una recomendación automática
El reporte es Markdown determinístico que el asesor revisa antes de compartir con el cliente. No hay botón de "enviar al cliente".
10. Generación del reporte — POST /cases/{case_id}/reports

Markdown determinístico que consolida la selección final. Sin PDF por ahora. Versionado por caso (UNIQUE(case_id, version)).

11. Resumen final compacto

Refresca el resumen del caso y muestra los flags del tramo de cartera + IDs derivados.

Pasos 12–15 · Evidencia para compliance
Audit trail, verificación de integridad, logs de IA, snapshot único
Cambiá el token del Dashboard a dev-compliance-token (o cualquier rol admin/compliance) antes de hacer clic en Verificar cadena de auditoría o Cargar logs de IA.
12. Audit Trail — GET /cases/{case_id}/audit

Lista cronológica de AuditEvent del caso (cadena hash SHA-256). Cualquier rol válido puede leer.

13. Verificación de auditoría — GET /cases/{case_id}/audit/verify

Recomputa la cadena hash y reporta is_intact. Requiere rol admin o compliance — cambiá el token del Dashboard a dev-compliance-token si hace falta.

14. Logs de llamadas a la IA — GET /cases/{case_id}/ai-logs

Llamadas a OpenAI persistidas para este caso. input_redacted es la versión sanitizada por el backend (texto libre + client_id redactados). Requiere rol admin o compliance.

Privacidad: raw_response y los campos fuera de la whitelist se guardan sin redactar a nivel API. Revisar antes de compartir exportes.
15. Snapshot de compliance

Vista combinada: summary + audit/verify + ai-logs en un solo render. Útil como handoff a compliance. Si el token actual no tiene admin / compliance, las sub-requests de verify / ai-logs aparecen como "skipped (403)".
